# Claude Code dashboard: decision log

Rationale for the choices in [plan.md](plan.md).

## 2026-10-29

- **Local web page, not a native app.** Faster to build, nicer UI per line of code. Clicking a row can still focus iTerm2, because the server runs AppleScript on the Mac.
- **No control actions (kill, message, stop).** Once a tab is focused they are one keystroke away in Claude Code itself: `/tasks` lists background shells and agents and stops them; Esc interrupts. The only action added is fork, which needs a new tab.
- **Live sessions only in the main list; a separate browser for the past.** Closed sessions vanish from the list. History is explored in the session browser, over whatever Claude Code keeps on disk (30-day `cleanupPeriodDays` default).
- **No notifications.** Idle sessions sort to the top and stand out visually instead.
- **Track directory changes.** Every transcript entry records its `cwd`, so the dashboard shows start dir, current dir and the path between them.
- **Fork goes through the shell instead of exec'ing claude.** A `claude` wrapper (one that picks the work or personal account by folder, say) only exists in the shell; running the command there keeps it (how it is started: 2026-11-02).
- **One page covers several accounts.** A second config dir (`~/.claude-work`) can be a symlink to `~/.claude`, so all sessions share one registry and one set of transcripts; each session's account comes from its process's `CLAUDE_CONFIG_DIR`.
- **Localhost only, Origin-checked actions.** Transcripts contain whatever passed through the sessions (possibly secrets), and fork runs a command. Binding to 127.0.0.1 keeps other machines on the network out; checking `Origin` stops a random website in your browser from silently calling the fork endpoint.
- **Reading undocumented files, isolated and fail-soft.** `~/.claude/sessions/*.json` and the tasks output layout are internal and may change with a Claude Code update. One reader module, tolerant parsing, "unavailable" instead of crashes.
- **Plan usage via the status line, optional.** Superseded on 2026-11-03: read from the usage endpoint instead.

## 2026-10-30

- **Branches only in the side panel.** "Branches with edits" lists every repo the session or its sub-agents changed files in, with each branch. The branch comes from the transcript when the edit was in the session's own repo, else from that repo's `HEAD`. Edits in folders that no longer exist (removed worktrees) can't be tied to a repo any more, so they are listed apart, collapsed.
- **Shell commands are parsed, never run.** Sessions read most files through Bash, so commands are tokenized like zsh would (quotes, heredocs, `cd`) and globs, braces, `~` and variables set in the same command are expanded in-process with `glob` (directory listings only). Running the commands, even "read-only" ones, was rejected: transcripts hold arbitrary text, and no command is reliably side-effect free. What needs execution to know (`$(...)`, `xargs` input, files a script opens) is left out, not guessed.
- **A local SQLite index for the session browser.** The transcripts add up to ~11 GB (10 GB of it sub-agents); a full read takes ~40 s. The index stores each file's reader state with its size and mtime, so a scan only re-reads changed files, from where it stopped. It lives in `~/Library/Caches/harness-watch/` because it is a cache: deleting it costs one full re-read. It mirrors what is on disk: sessions Claude Code deletes after 30 days drop out (keeping them would be a one-line change).
- **Running state read from the transcripts, not guessed from activity.** A background shell or monitor runs from its launch result until its `<task-notification>` (or a TaskStop). A sub-agent runs while its transcript is mid-turn (last entry a tool call or a result, its `SubagentHandback` excepted), until a notice newer than its last entry. Nothing runs in a closed session, or if it started before the current process (a resumed session's earlier tasks died with that process). Recent-file-write heuristics were rejected: a sub-agent waiting minutes on one command writes nothing.
- **Totals include sub-agents.** The Tokens column, the cost and the All sessions list count the main transcript plus every sub-agent; the side panel splits them. Context % stays the main session's, as that is what fills up.
- **Processes from `ps`, matched by command.** A Claude Code Bash tool runs as `zsh -c '… eval '<command>' …'` under the `claude` process, so its command is recovered exactly and a background shell is linked to its process by identical command text. Other children (MCP servers, `caffeinate`) are listed apart.
- **Statuses that need you sort first, limits last.** `waiting` (a question or permission), then `idle` and `shell`, share the idle colour; `busy` and the rest follow. A session blocked by its account's usage limit goes to the end with its own colour, whatever its status.
- **A usage limit is per account.** Claude Code writes a hit into the transcript ("You've hit your session limit · resets 1pm (…)"). The latest hit across the live sessions of one account (incl. sub-agents) marks all of them, until its reset time, a later real response in any of them, or "Usage limit reset". Closed sessions don't count: their account isn't known.
- **Tool calls live in the index.** ~70k calls are spread over 11 GB of transcripts (22k in the largest session), too slow to parse when a panel opens. The index stores each call as it reads the transcripts anyway (input capped at 4 KB, result's first 600 characters), which costs nothing extra in scan time and grows the cache from ~20 MB to ~185 MB. A running session's explorer reads that session's new lines on each request, so it is current without waiting for the 30 s rescan. Files are grouped by tool in the explorer; their directory trees stay in the Files sections.

## 2026-11-02

- **Flow messages are read where they arrive.** Every message an agent gets lands in its own transcript as a user entry: a sub-agent's prompt, `<teammate-message>` (SendMessage, idle notices), `<agent-message>` (hand-back reports), `<task-notification>`, and a foreground agent's result on the Agent call. Reading the receiving side catches all of them, including ones the sender's call doesn't show (idle notices, notifications). Senders are stored as written (a name like `team-lead`, an agent id) and resolved to lanes when the flow is built, once every agent's name is known; a name that matches no agent of the session is shown as an outside lane. Notices Claude Code itself adds to a sub-agent (`[SYSTEM NOTIFICATION…]`, `[handback-send-enforce]`, skill bodies) are not messages.
- **Activity spans, not one bar per agent.** Teammates sit idle for hours between messages, so a bar from first to last activity would hide when they worked. A lane's bar breaks after 5 minutes without a tool call or message, and the time axis cuts out stretches of 10+ minutes when nothing ran at all (a session spanning days stays readable).
- **Fork starts the tab with its command; nothing is typed.** Typing the command into the new tab (`write text`) sometimes landed in another tab, the one with the keyboard focus. Now the tab's own process is the login shell running a script (fish only until 2026-11-07, then zsh and bash too, started interactive so their functions load): the script `cd`s to the start dir, runs `claude --resume <id> --fork-session --name <name>` through any `claude` wrapper, then `exec`s a login shell so the tab stays usable. The script sits in a file (`~/Library/Caches/harness-watch/forks/<id>.fish` or `.sh`, rewritten per fork) so iTerm2 only gets a plain path to parse, never a quoted path or name.
- **A fork gets its own name.** It would otherwise inherit the original's title. The name field is prefilled with "<title> (fork)"; `--name` sets what the prompt box, the `/resume` picker and the tab title show.

## 2026-11-03

- **Plan usage from the endpoint `/usage` calls, not the status line.** The status-line JSON is the only documented source of the limits, but a status line (even an empty one) adds a row to every session and hides footer hints like `esc to interrupt`. The dashboard calls `api/oauth/usage` instead, the endpoint Claude Code's `/usage` reads, with the account's login from the Keychain: it works with no session open and gives the same bars as the Claude app. Accepted risks: the endpoint is internal (a change shows "unavailable", not a crash), and the dashboard reads a login token (it goes only to Anthropic's API, as from Claude Code, and is never logged). The token is never refreshed: a refresh would replace Claude Code's own login and could sign it out; an expired one is reported until a session renews it.
- **Read every 5 minutes, and just after a window resets.** The endpoint rate-limits (Claude Code itself backs off on 429), so the dashboard honours Retry-After, else waits 10 minutes.

## 2026-11-04

- **A name without a port, on its own loopback address, 127.0.0.2.** Dropping `:8787` needs port 80, which only root may listen on; running the server as root was rejected (it drives iTerm2 and reads your files as you). A pf rule forwards port 80 to 8787 instead. Forwarding 127.0.0.1:80 would take `localhost:80` from everything else (Docker, a local nginx), so the name gets an address of its own: `/etc/hosts` maps it to 127.0.0.2, and a root LaunchDaemon adds that address to loopback at boot and forwards only its port 80. A `.localhost` name can't do this: Chrome sends every `.localhost` name to 127.0.0.1 and ignores `/etc/hosts` for them. The rule sits in its own anchor under `com.apple`, which `/etc/pf.conf` already evaluates, so that file stays untouched (macOS updates rewrite it). Cost: Chrome reads a bare name as a search until it was opened once with `http://`. The bare name is an allowed host; the DNS-rebinding check still rejects every other name.
- **A relay process instead of the pf forward.** The pf rule stopped working the same day: NordVPN loads its own pf rules (`rdr-anchor "main/*"`) over macOS's, which drops the `com.apple/*` hook our anchor hung on, and nothing re-adds it until the next boot. Any app that manages pf (VPNs, firewalls) can do this. Now `relay/relay.py`, run by the root LaunchDaemon `harness-watch.relay`, listens on 127.0.0.2:80 itself and copies bytes to 127.0.0.1:8787, so pf is not involved. It binds as root, then runs as nobody; the server still runs as you (iTerm2, Keychain). It uses only `/usr/bin/python3`'s standard library and is copied to a root-owned path (`/Library/PrivilegedHelperTools`), since root must not run a file the user can edit. KeepAlive restarts it if it dies.
- **Plan usage from the status line by default; the Keychain reading moved out of the repo.** Anthropic's terms (code.claude.com/docs/en/legal-and-compliance) bar developers from collecting or intermediating Claude.ai login tokens, which the 2026-11-03 source did, so a public version can't ship it. The status line's `rate_limits` are documented and handed over by Claude Code itself. Costs: they need a status line, cover only Pro, Max and Ultra, and update only while a session runs (a reading older than 10 minutes shows "as of"). Another source can still be plugged in from a file named by `HARNESS_WATCH_USAGE_SOURCE`: one codebase, nothing to merge, the file adapted only if the feed's shape changes. A source that fails to load falls back to the status line, logged.
- **The agent runs the main checkout.** A worktree disappears when its feature merges. After a merge, `launchctl kickstart -k gui/$(id -u)/harness-watch` restarts it and open pages reload themselves; a hand-started dev server needs another port (`HARNESS_WATCH_PORT=8788`).

## 2026-11-07

- **Named harness-watch, ready to publish.** Anthropic's terms forbid "Claude Code" or "Anthropic" in a product's name, so the package, commands, variables (`HARNESS_WATCH_*`) and cache dir took a name of their own; the README says plainly that Claude Code is the only harness supported for now. Nothing in the code is specific to one machine any more: `install-agent` writes the LaunchAgent for whoever runs it (keeping the `HARNESS_WATCH_*` and `CLAUDE_CONFIG_DIR` variables set then), the extra host name comes from `HARNESS_WATCH_HOSTNAME`, and the relay's files carry no user's label.
- **The page needs a key.** Every account on a Mac can reach 127.0.0.1, and the Host and Origin checks only stop websites (curl sets any header), so another account could read every transcript and open fork tabs. The server keeps a random key (`~/Library/Application Support/harness-watch/key`, 0600, written whole or not at all; not in Caches, which macOS may purge) and answers `/api/` only with it. How it reaches the browser, each choice closing a leak the review found: `harness-watch open` first asks the server for an HMAC of a fresh nonce (whoever holds the port must prove it has the key), then opens a 0600 local file whose form POSTs the key (a URL argument shows in `ps` to every account, and an address stays in history); the server answers with a page that puts it in localStorage (a cookie would go to every port of 127.0.0.1, other accounts' servers too) under a nonce-only CSP, and the page sends it as a header (as `?key=` for the event stream, which can't send headers). The page's own files need no key: they hold no data and tell you to run `harness-watch open`. Cost: once per browser and per address. Not covered: another account grabbing the port during a restart while a page is open.
